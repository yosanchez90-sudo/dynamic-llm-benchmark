# Comparison C — pre-registered analysis plan

**Pre-registered 2026-07-26, before POST-fine-tune evaluation exists**, per the
2026-07-25 decision to proceed with the 1,017-record verified ULT training set
(28.0% core_400 coverage) instead of waiting for or engineering toward full coverage.
`data/raw/ult_plt/PROVENANCE.md` has the repair pipeline and taxonomy this plan
is built on, and `data/raw/ult_plt/comparison_c_seen_manifest.json` (generated by
`scripts/build_comparison_c_seen_manifest.py`, frozen 2026-07-26) has the exact
seen/unseen split this document analyses.

## Design

Two framings, both reported (not either/or):

1. **Aggregate 2x3 DiD** (original design, PROJECT_BRIEF.md Sec 7/Sec 3.1 H2):
   pre/post fine-tune x {ULT core_400, PLT core_400, Dynamic}. Kept for continuity
   with the approved design and cross-referencing against the six supplementary
   Dynamic-trained runs.
2. **Stratified core_400 ULT, by seen-in-training** (new, this document): split
   core_400's 400 ULT problems into seen (n_problems=112, has a verified training pair) vs
   unseen (n_problems=288, does not) using the frozen manifest above. A problem's
   seen/unseen status is fixed at manifest-generation time and must not be
   recomputed from a re-run of the repair pipeline mid-experiment.

## Primary estimand

DiD of the **seen-ULT gain** (POST metric − PRE metric, mean over the 112 seen
core_400 ULT problems) vs the **Dynamic gain** (POST − PRE on the Dynamic
benchmark control, same instantiations as the six supplementary runs, per Part 2
item 4's "same instantiations as the supplementary study for consistency"). This
isolates a contamination-specific effect from a generic "fine-tuning improves
everything" effect.

**Metric choice, flagged not assumed:** PROJECT_BRIEF.md declares Mut@K the
project-wide headline metric, but the confounder audit below found the PRE side of
this cell has Mut@K defined for only **1 of 112** seen problems (baseline_passed
is false for the other 111, detailed in "PRE data sparsity" below). Recommend
**baseline_pass_rate** (fraction of problems with `baseline_passed=True`) as the
*primary* metric for this specific DiD cell: it is defined for all 112/288
problems regardless of whether the suite happens to also kill mutants, and it is
exactly the metric the six supplementary runs already used as their headline
contamination signature (`analysis/FINETUNE_ENDPOINT_PROVENANCE.md`'s "seen (inst1)
54.0%" language is a baseline-pass rate, not a Mut@K value). Report Mut@K
alongside as the dissertation's declared headline metric, but computed only over
the (necessarily small, PRE-side-limited) subset where baseline passes both
pre and post, with the n made explicit, not implied.

## Dynamic arm tier composition (amendment, pre-registered 2026-07-26 before any
## Dynamic POST row exists for the canonical adapter — not a post-hoc choice)

The design above names "the Dynamic benchmark control" without pinning down tier
scope. Evaluate POST Dynamic on **all four tiers (L1-L4)**, instantiations 1-3
(matching the six supplementary runs, per Part 2 item 4's "same instantiations as
the supplementary study for consistency", same instantiations, same resolved
generation config, read from the actual PRE rows, not assumed). Report the
Dynamic arm **two ways**, both reported, not either/or:

(a) **Tier-matched L4**: the CC-fair comparison against ULT/PLT's CC>=8 band,
    matching `src/Analysis/comparison.py`'s existing Comparison-A convention.
    Explicitly **floor-limited**: Qwen-1.5B base PRE has `mutation_score` defined
    for **0/225** L4 problems across inst1-3 (`baseline_pass_rate`=0.000,
    `exec_rate`=0.564), a complete floor, not a low-but-real baseline.
(b) **L1-L3 pooled**: where the base model has real (if partial) headroom:
    PRE `exec_rate`=0.852, `baseline_pass_rate`=0.067, `mutation_score` defined for
    45/675 problems (vs 0/225 at L4). Per-tier PRE detail: L1 exec=0.916
    baseline_pass=0.031 mut_defined=7/225; L2 exec=0.898 baseline_pass=0.164
    mut_defined=37/225; L3 exec=0.742 baseline_pass=0.004 mut_defined=1/225.
    L3 alone is nearly as sparse as L4, which is why L1-L3 is pooled instead of
    each tier reported as its own arm.

**Reason for specifying this now, not after POST lands:** floor effects make an
L4-only null uninterpretable: it cannot distinguish "fine-tuning on ULT genuinely
doesn't transfer to Dynamic" (the contamination-resistance prediction) from "the
metric structurally cannot move because PRE was already at the floor with nothing
to measure a gain against." (a) stays the primary, CC-matched DiD cell (paired with
seen-ULT/unseen-ULT/PLT, all CC>=8) but is flagged floor-limited wherever reported.
(b) is the arm where a null result is actually informative, reported alongside as
the interpretability check the design above was missing.

## Secondary estimand: four-level contamination gradient

seen-ULT (n_problems=112) → unseen-ULT (n_problems=288) → PLT core_400 excl. ULT overlap (n_problems=400) →
Dynamic-L4 (fresh instantiation, no static leakage, CC-matched per the tier
amendment above, flagged floor-limited there. L1-L3 pooled reported alongside as
a separate, non-CC-matched robustness point, not a fifth gradient step).

**Memorization signature** = monotone decay of (POST − PRE) gain along this
ordering: gain(seen-ULT) > gain(unseen-ULT) > gain(PLT) > gain(Dynamic) ≈ 0. This
is the sharper, more falsifiable test of contamination resistance: even with only
28% core_400 coverage, a genuine training-content effect should show up as a step
down at exactly the seen/unseen boundary within ULT (a within-benchmark,
same-CC-band contrast, detailed in the confounder audit below), not just at the coarser
ULT-vs-Dynamic level.

## Statistical approach

- Bootstrap CIs (n_boot=2000, matching `src/Analysis/comparison.py`'s existing
  convention) for every gain estimate and every pairwise gap along the gradient.
- Report the aggregate (unstratified) 2x3 table alongside the stratified version,
  not as a replacement for it.

## Confounder audit (`analysis/comparison_c_confounder_audit.csv`, 2026-07-26)

Seen (n_problems=112) vs unseen (n_problems=288) core_400 ULT problems, Mann-Whitney U (normal
approx.), two-sided:

| Metric | seen mean | unseen mean | z | p |
|---|---|---|---|---|
| CC | 14.82 | 14.97 | 0.30 | 0.761 |
| code length (chars) | 1,224 | 1,533 | −2.41 | **0.016** |
| PRE exec_rate (Qwen-1.5B base) | 0.571 | 0.684 | −1.75 | 0.080 |
| PRE mutation_score (n_problems=1 seen / n_problems=7 unseen, detailed below) | 0.886 | 0.338 | 1.53 | 0.127 |

Band distribution (seen / unseen): CC8-9 5/15, CC10-11 38/97, CC12-15 32/97,
CC16+ 37/79. This is proportionally similar across bands, consistent with the
CC-match (p=0.76) above.

**Reading this table:** seen problems are **significantly shorter** (p=0.016):
expected, since the repair pipeline's auto-repair only handles the simple
`assert x == y` shape, and shorter functions are more likely to have simple
ground-truth tests and fewer missing-import structural failures. CC itself is
well-matched (p=0.76), which is the more direct proxy for the RQ2-relevant
"difficulty" confound this project already tracks. PRE exec_rate is marginally
lower for seen (p=0.08, not significant at 0.05). DiD differencing (comparing
*gains*, not levels) and the Dynamic-benchmark control both partially absorb a
level confound like code length, but a length-driven confound in the *gain itself*
(e.g. if shorter functions are also easier to memorize AND easier to generalize
on) is not fully ruled out by this audit, noted, not resolved.

## PRE data sparsity — found while building this audit, load-bearing for metric choice

Qwen-1.5B **base** model's already-landed PRE evaluation on ULT core_400
(`data/results/ult/Qwen__Qwen2.5-Coder-1.5B-Instruct__ult__zero_shot__instcore_400__20260713T123923.jsonl`)
has `baseline_passed=True` for only **1/112 (0.9%)** of the seen subset and
**7/288 (2.4%)** of the unseen subset. Mutation score is therefore defined for
essentially none of core_400 ULT pre-fine-tune: a base 1.5B model struggling at
CC≥8 (consistent with the same model's near-zero L4 Dynamic mutation-score
coverage noted in this pass's Part-1 status check). This is *why* the primary
metric recommendation above is baseline_pass_rate, not Mut@K: an n_problems=1 PRE cell
makes any Mut@K-based gain estimate for seen-ULT close to undefined, regardless of
how POST turns out.

## Power

Seen-cell (n_problems=112), worst-case SE for a proportion-style metric (baseline_pass_rate)
is `sqrt(0.25/112) ≈ 0.047`, adequate to detect contamination-scale effects: the
six supplementary runs' seen/unseen memorization gaps were 50-70 percentage
points (`analysis/FINETUNE_ENDPOINT_PROVENANCE.md`), many multiples of this SE.

## Contingency

If the seen-ULT DiD result comes back marginal (CI overlapping zero, or
overlapping the Dynamic-control estimate), exercise the SHAPE_NOT_REPAIRABLE
repair extension flagged in `data/raw/ult_plt/PROVENANCE.md` (ceiling ~53% of the
full ULT pool vs today's 34.1%) to increase n before concluding a null result.
Not attempted proactively. Engineering it now would spend time before knowing
whether it's needed.
