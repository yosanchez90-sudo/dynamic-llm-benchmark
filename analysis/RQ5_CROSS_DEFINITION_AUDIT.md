# Mut@K cross-definition audit — this project vs the ULT/PLT paper

Resolves the `src/eval/test_gen_scorer.py` TODO ("KILLED DEFINITION ...
CONFIRM this against ULT's methodology"), left open since that scorer was
first written. Hand-written, zero-compute — checked the ULT/PLT paper's
own published methodology against this project's scorer code.

## This project's definition (exclude / conditional mean)

`src/eval/test_gen_scorer.py::score_problem`: if the generated suite does
not pass on the original function (`baseline_passed=False`), the row's
`mutation_score` is set to `None`. Every downstream mean (`Mut@K` as
computed throughout `analysis/RQ5_*.md`, `analysis/COMPARISON_*.md`) is a
`.dropna().mean()` — i.e. **the mean is taken only over baseline-passing
rows**. A model that produces a passing suite for 5% of problems and a
non-passing suite for 95% gets averaged only over that 5%, same as a model
that passes 95% of the time.

## The ULT/PLT paper's definition (include-as-zero / unconditional mean)

Source: Huang & Du et al., ACM TOSEM / arXiv:2508.00408 (the paper this
project's ULT/PLT datasets are sourced from — `data/raw/ult_plt/PROVENANCE.md`),
Section 3.4.3. Fetched live 2026-07-30 (`WebFetch` against
`arxiv.org/html/2508.00408v1` — not a PDF-parsed or offline copy, flagged
per this project's own citation-verification standard).

The paper's stated formula: **`Mut@k = Σ(i=1 to N) Mi / N`**, with **N
explicitly defined in-text as "the total number of functions in the
benchmark"** — not "the number of functions whose generated suite passed
on the original." The fetched excerpt did not surface a sentence stating
Mi's value for a non-passing suite explicitly (a genuine gap in the paper's
own exposition, not filled in here by guessing) — but given N is pinned to
the *fixed, full benchmark size* rather than a per-model passing subset,
**the only reading consistent with the paper's own stated formula is
Mi=0 for a non-passing function, included in the N=total-functions
denominator**. If the paper intended an exclude/conditional definition, N
would necessarily vary per model (as the passing count does), which
contradicts N being introduced as a fixed benchmark-size constant.

**This is an inference from the stated formula, not a directly quoted
confirmation — stated with that caveat, not asserted as certain.** A
reader with direct access to the paper's full PDF (with equations rendered,
which the HTML-fetch pipeline used here does not perfectly preserve) should
verify this against Section 3.4.3 directly before treating it as settled
beyond reasonable doubt.

## Consequence: these are different estimands, not different values of the same one

This project's Mut@K and the ULT paper's own Mut@K are not offset by a
constant or comparable via a simple correction — they are different
statistics even applied to identical (function, model) pairs:

- This project's Mut@K = mean(per-function mutation score | baseline passed)
- The paper's Mut@K = mean(per-function mutation score, zero-filled where
  baseline failed) = **this project's Mut@K × baseline_pass_rate**

That second line is exactly this project's own `coverage_adjusted` score
(`scripts/analyze_rq5_diagnostics.py` sec 3, `scripts/analyze_rq5_cross_family.py`),
introduced this session as a post-hoc robustness re-scoring. **It is not
merely a robustness check — it is the metric that actually matches the
ULT paper's own published methodology.** The pre-registered primary
conditional Mut@K is a different, project-specific estimand that happens to
share the paper's metric name.

This also explains a gap that was never flagged before: this project's own
Mut@K values for its evaluated models run roughly 0.75–0.97 (see
`analysis/rq5_model_ranking.csv`), while the ULT paper itself reports "test
cases generated by LLMs only achieve ... 40.21% for mutation score on
average for all LLMs" (its own abstract). These are not describing the same
models, so the gap isn't itself evidence of anything — but a reader who
assumed the two numbers were the same estimand and directly comparable
would (wrongly) read this project's models as roughly 2x better at test
generation than the paper's, when a large share of that gap is
definitional, not capability.

## What this means for reported numbers

**Every Comparison A/B and RQ5 number built from conditional Mut@K (the
pre-registered primary metric) should be read as this project's own
metric, not as directly comparable to any number the ULT/PLT paper itself
publishes.** Concretely:

- `analysis/COMPARISON_PROVENANCE.md`'s primary Comparison A/B tables use
  conditional Mut@K — flagged there directly (see that file's
  cross-definition note, added alongside this audit).
- `analysis/RQ5_INTERPRETATION.md` / `analysis/RQ5_DIAGNOSTICS.md`'s
  headline τ=0.143 result and its coverage-adjusted τ=0.905 counterpart are
  BOTH internal to this project (Dynamic vs ULT, both scored by this
  project's own harness on both sides) — the cross-definition risk does
  NOT apply there, since both arms of that comparison use the identical
  scorer and identical (exclude-based) definition. The cross-definition
  risk is specific to any claim that compares this project's numbers
  against the ULT/PLT paper's OWN published figures, which
  `analysis/RQ5_CROSS_FAMILY_PROPOSAL.md`/`RQ5_INTERPRETATION.md` never do
  (BigCodeBench, the RQ5 public-benchmark comparator, is a separate paper
  with its own Pass@1 metric, not mutation score, so this specific
  cross-definition issue does not apply to the BigCodeBench comparisons
  either).
- The one place a direct ULT-paper-vs-this-project comparison could
  plausibly appear in future write-up (e.g. "how does our harness's
  mutation score on ULT's own dataset compare to the paper's own reported
  average") should use `coverage_adjusted`, not conditional Mut@K, as the
  metric that actually matches the paper's own definition.
