This file was requested as part of a Phase-V verification pass as a
standalone quarantine notice. **`analysis/README.md` already covers this
exact ground** (root cause, date range, pointer to the corrected data) and
was written as part of the same fix commit (`afc11ca`). This file exists
because the verification task asked for it by name; read it as a

**Do not edit or delete any `epoch_perf_finetune_*.csv` file — append-only
applies to this quarantine too.**

## Root cause (same as `analysis/README.md`)

`scripts/eval_checkpoints.py` carried an uncommitted change, added
2026-07-07 and sitting in the working tree until the fix was committed on
2026-07-12 (`afc11ca`), that passed `no_repeat_ngram_size=4` to
`model.generate()`. HF's n-gram repeat ban applies over the full
prompt+response sequence; the fixed system prompt contains the literal
phrase `from under_test import <function_name>` as a formatting
instruction, so any checkpoint that correctly emitted that line got it
corrupted on regeneration (`from under_testimport format_value`,
`from under_test imporformat_value`, etc.) — breaking the Python syntax and
failing the exec gate. Confirmed directly: `data/results/debug_collapse/finetune_qwen7b_bp_own_30ep__epoch30_healthy_control__configA_evalcheckpoints__raw.jsonl`
(10/10 corrupted import lines, `no_repeat_ngram_size=4`) vs
`...configB_original_baseline__raw.jsonl` (10/10 clean, same checkpoint,
same problems, setting removed).

as "Contaminated"** and its headline states **"Four of the six files."**

## Why the Phase-1b diagnostics looked like a contradiction (and weren't)

`scripts/diagnose_collapse_full150.py` reproduced the *exact* (epoch=30,
instantiation=2) cell for `qwen7b_bp_own` — all 150 problems, real
`eval_checkpoints.py` functions, original V100 hardware — and got
`exec_rate=0.0`, against "Real recorded CSV value for this exact cell:
exec_rate=1.0 baseline_pass=0.5333" (see
`logs/diagnose-collapse-full150-9371310.out`). Read in isolation this looks
like a contradiction in the same cell. It isn't: the recorded CSV value was
measured on 2026-07-06, before the bug existed; every diagnostic script
that reproduced the 0.0 result ran on 2026-07-11/07-12, by which time
`eval_checkpoints.py`'s working tree already carried the unfixed
`no_repeat_ngram_size=4`. Same cell, same checkpoint, two different
generations of the evaluation script — not a contradiction, a timing gap.

`scripts/diagnose_collapse_v100.py` ("Phase-1b Step 5", the hardware
control) ran the "healthy control" (`bp_own`) and "primary suspect"
(`bp_gpt5`) checkpoints back-to-back and **both arms came back
`exec_rate=0.0, n_problems=10`** (`logs/diagnose-collapse-v100-9369140.out`). This
was not a true A/B toggle — `gen_cfg` in that script hardcodes
`no_repeat_ngram_size=4` for both checkpoints (`scripts/diagnose_collapse_v100.py:77`)
— so both arms were run under the identical buggy config, on two different
checkpoints. That both failed identically was the tell that the corruption
tracked the shared generation config, not either checkpoint's own
fine-tuning trajectory, and is what redirected the investigation toward
`scripts/diagnose_collapse_ab.py`'s true config-A-vs-config-B test, which
isolated the setting.

## Open gap: the 240s wall-clock guard may not cover job 9315777's actual failure mode

Added 2026-07-14, re-examining the job 9315777 hang more closely rather
than taking the module docstring's framing ("a genuine safeguard") at
face value.

**Where it stalled, exactly:** `logs/eval-ckpts-9315777.out` shows
generation dots for epoch 5/instantiation 1 stop at 74/150 — no
`inst1: scoring…` line ever printed, so the process was inside
`model.generate()` for problem 75, not in a scoring subprocess, when it
stopped producing output. `logs/eval-ckpts-9315777.err`'s last line is the
checkpoint-shard loading progress bar from job start; nothing after it
until SLURM's cancellation message 11.5 hours later. No partial-generation
text, no exception, no further tokenizer/model output of any kind.

**Why this doesn't look like "slow generation":** `max_new_tokens=2048`
caps every call, and measured worst-case throughput (15.8 tok/s, see the
module docstring) puts a full 2048-token generation at ~130s even in the
slowest observed case. 11.5 hours of *zero* incremental output — not
slow-but-progressing output, literally nothing — is inconsistent with "the
model is just grinding through 2048 tokens." It is consistent with the
generate() call being genuinely stuck (a CUDA/driver-level hang on that
V100 node, not a content-driven repetition loop).

**Why the `_TimeLimitCriteria` guard may not actually cover this:**
`StoppingCriteria` callbacks in HF's `generate()` loop are invoked
*between* successfully generated tokens — the loop calls the model
forward pass, gets a token, then checks stopping criteria, then repeats.
If the hang is inside a single forward-pass call itself (consistent with
the evidence above — no partial progress, ever), the stopping-criteria
callback is never reached again, and the 240s wall-clock check never
fires. What actually terminated job 9315777 was SLURM's own job-level
`--time` limit (12h), not anything inside the Python generation loop. The
current guard protects against "many slow steps add up to a long time,"
which is a real but different failure mode from "one step never returns."

**Fixed 2026-07-14** (all 66 shards had finished by the time this was
addressed, so this no longer competes with anything running). Added
`_ProcessWatchdog` to `scripts/eval_checkpoints.py`: a background thread,
kicked immediately before every `generate()` call, that calls `os._exit(99)`
if no call has completed within `--watchdog-timeout` (default 900s — ~7x
the slowest measured single generation). This works around the
`StoppingCriteria` limitation because PyTorch's CUDA calls release the GIL
while blocked on the device, so the watchdog thread keeps running and can
force-exit the process even while the main thread is wedged inside a
single stuck `generate()` call that will never return — no cooperation
from the stuck call is required, unlike `StoppingCriteria` or a signal
handler. This kills the whole shard (not just the stuck problem), which is
intentional: there's no way to safely abandon one CUDA call and continue
in the same process, and the existing sharded-submission design already
treats "resubmit the failed shard" as normal recovery — this just detects
the failure in minutes instead of waiting out the full `--time` limit.
Covered by `tests/test_eval_checkpoints_watchdog.py` (4 tests, run in a
real subprocess so `os._exit` can be exercised without killing the test
runner: fires when never kicked, doesn't fire when kicked regularly,
`stop()` suppresses it, and `--watchdog-timeout 0` disables it via `main()`
rather than constructing a watchdog that fires immediately).

## Subprocess timeout audit (eval/scoring path)

Every `subprocess.run()` call in the eval/scoring hot path has an explicit
`timeout=`:

| Call site | Timeout |
|---|---|
| `src/eval/test_gen_scorer.py:156` (`_run_pytest`) | explicit, caller-supplied |
| `src/eval/test_gen_scorer.py:173` (`_collect_ok`) | explicit, caller-supplied |
| `src/eval/test_gen_scorer.py:209` (`_evaluate_mutant`'s import check) | explicit, caller-supplied |
| `scripts/eval_checkpoints.py:95` (`_score_fast` import check) | explicit, default 60s |
| `scripts/eval_checkpoints.py:103` (`_score_fast` pytest run) | explicit, default 60s |

One call outside that hot path had **no timeout**:
`scripts/submit_epoch_curve_shards.py`'s `sbatch` submission call
(`subprocess.run(cmd, cwd=ROOT, capture_output=True, text=True)`). Lower
risk than a generation/scoring hang (a stuck `sbatch` stalls job
*submission*, not an in-flight run, and wouldn't corrupt results), but a
real gap: if `sbatch`/`slurmctld` ever hung, this call would block forever
with no recovery. **Fixed 2026-07-14**: added `timeout=30` with a
`subprocess.TimeoutExpired` handler that raises a clear `RuntimeError`
instead of hanging the whole submission loop.

## Also fixed while investigating: flat `--mem` OOM-killed 3 shards

Not part of the original stall investigation, but found while confirming
all 66 shards had actually finished: `sacct` showed 63 `COMPLETED` and
**3 `OUT_OF_MEMORY`** — jobs `9372594`, `9372595` (`qwen1_5b_bp_gpt5`,
epochs 3/5) and `9372627` (`qwen7b_bp_gpt5`, epoch 3), all 6.5–8.5h into
an 8h-budgeted run. `run_eval_checkpoints_shard.slurm` requested a flat
`--mem=16G` for every shard regardless of model size or condition — too
tight for a 7B model (14GB bf16 weights alone) and, evidently, also too
tight for `bp_gpt5` (the long-output condition) even at 1.5B, given enough
elapsed time. Fixed by adding `_mem_for(config_name, is_slow)` to
`scripts/submit_epoch_curve_shards.py`, sizing `--mem` per size × condition
(24G/40G/32G/56G for 1.5B-fast/1.5B-slow/7B-fast/7B-slow) and passing it
via `sbatch --mem=...` (CLI wins over the `.slurm` file's `#SBATCH`
pragma). Covered by `tests/test_submit_epoch_curve_shards.py`, so a future
flat-mem regression would fail CI, not just get caught after an 8h run.

**No resubmission was needed.** Checked the 3 shards' own CSV output
before resubmitting anything: each already contained all 3 expected
(epoch, instantiation, draw) rows for a single-epoch greedy-only shard,
with plausible values and a fully resolved generation config — e.g.
`data/results/finetune_rebuild/shards/finetune_qwen7b_bp_gpt5_30ep__epoch03.csv`
has 3/3 rows, exec_rate 0.83-0.93. The CSV mtimes line up almost exactly
with the OOM event timestamps in each `.err` file, meaning the OOM killer
struck during process teardown (CUDA context/tokenizer cleanup, Python GC
at exit) *after* every row had already been written — rows are appended
to disk immediately as each is computed, per `eval_checkpoints.py`'s
resume-on-restart design, so nothing was lost. Confirmed with the
authoritative check: `python scripts/merge_epoch_curve_shards.py --manifest
data/results/finetune_rebuild/shards/manifests/manifest_20260712T222551Z.csv
--check-only` reports **all 6 conditions complete, 36/36 expected triples
each** (216 rows total) — that check reads shard CSV content directly and
doesn't care what SLURM's `sacct` state says. Resubmitting would have
spent GPU time to regenerate data that already exists and would just be
skipped by the resume logic.
