# Quarantine notice: `epoch_perf_finetune_*.csv` (pre-fix)

This file was requested as part of a Phase-V verification pass as a
standalone quarantine notice. **`analysis/README.md` already covers this
exact ground** (root cause, date range, pointer to the corrected data) and
was written as part of the same fix commit (`afc11ca`). This file exists
because the verification task asked for it by name; read it as a
**correction layer on top of `analysis/README.md`**, not a duplicate —
one claim in that file does not match the underlying CSV data, and that
discrepancy is documented here with evidence rather than silently fixed.

**Do not edit or delete any `epoch_perf_finetune_*.csv` file — append-only
applies to this quarantine too.**

## Root cause (same as `analysis/README.md`)

`scripts/eval_checkpoints.py` carried an uncommitted change, added
2026-07-07 and sitting in the working tree until the fix was committed on
2026-07-12 (`afc11ca`), that passed `no_repeat_ngram_size=4` to
`model.generate()`. HF's n-gram repeat ban applies over the full
prompt+response sequence; the fixed system prompt contains the literal
phrase `from under_test import <function_name>` as a formatting
instruction, so any checkpoint that correctly emitted that line got it
corrupted on regeneration (`from under_testimport format_value`,
`from under_test imporformat_value`, etc.) — breaking the Python syntax and
failing the exec gate. Confirmed directly: `data/results/debug_collapse/finetune_qwen7b_bp_own_30ep__epoch30_healthy_control__configA_evalcheckpoints__raw.jsonl`
(10/10 corrupted import lines, `no_repeat_ngram_size=4`) vs
`...configB_original_baseline__raw.jsonl` (10/10 clean, same checkpoint,
same problems, setting removed).

## Discrepancy with `analysis/README.md` — flagged, not corrected here

`analysis/README.md`'s table marks **`epoch_perf_finetune_qwen7b_bp_own_30ep.csv`
as "Contaminated"** and its headline states **"Four of the six files."**
Both are contradicted by direct evidence:

1. **Timestamp**: the file's mtime is 2026-07-06 03:18, generated by job
   `9315776` — one day *before* `no_repeat_ngram_size=4` was added
   (2026-07-07, per both `scripts/eval_checkpoints.py`'s own docstring and
   `analysis/README.md`'s own "Root cause" section). A file measured before
   a bug existed cannot carry that bug.
2. **Content**: every row in the file is healthy — `exec_rate` ranges
   0.9867–1.0 and `baseline_pass` ranges 0.3333–0.6200 across all 30 epochs
   and all 3 instantiations. There is no row anywhere near 0.

This is why `finetune_qwen7b_bp_own_30ep` is labelled `"epoch30_healthy_control"`
in the diagnostic scripts (`diagnose_collapse_ab.py`, `diagnose_collapse_v100.py`,
`diagnose_collapse_full150.py`) — it was the non-collapsed baseline the
investigation compared the genuinely-collapsed conditions against, which
only makes sense if it was never itself contaminated.

## Why the Phase-1b diagnostics looked like a contradiction (and weren't)

`scripts/diagnose_collapse_full150.py` reproduced the *exact* (epoch=30,
instantiation=2) cell for `qwen7b_bp_own` — all 150 problems, real
`eval_checkpoints.py` functions, original V100 hardware — and got
`exec_rate=0.0`, against "Real recorded CSV value for this exact cell:
exec_rate=1.0 baseline_pass=0.5333" (see
`logs/diagnose-collapse-full150-9371310.out`). Read in isolation this looks
like a contradiction in the same cell. It isn't: the recorded CSV value was
measured on 2026-07-06, before the bug existed; every diagnostic script
that reproduced the 0.0 result ran on 2026-07-11/07-12, by which time
`eval_checkpoints.py`'s working tree already carried the unfixed
`no_repeat_ngram_size=4`. Same cell, same checkpoint, two different
generations of the evaluation script — not a contradiction, a timing gap.

`scripts/diagnose_collapse_v100.py` ("Phase-1b Step 5", the hardware
control) ran the "healthy control" (`bp_own`) and "primary suspect"
(`bp_gpt5`) checkpoints back-to-back and **both arms came back
`exec_rate=0.0, n=10`** (`logs/diagnose-collapse-v100-9369140.out`). This
was not a true A/B toggle — `gen_cfg` in that script hardcodes
`no_repeat_ngram_size=4` for both checkpoints (`scripts/diagnose_collapse_v100.py:77`)
— so both arms were run under the identical buggy config, on two different
checkpoints. That both failed identically was the tell that the corruption
tracked the shared generation config, not either checkpoint's own
fine-tuning trajectory, and is what redirected the investigation toward
`scripts/diagnose_collapse_ab.py`'s true config-A-vs-config-B test, which
isolated the setting.
