# Hypothesis coverage audit — H1 through H6 vs PROJECT_BRIEF.md §3.1

For each hypothesis in PROJECT_BRIEF.md §3.1's table: (i) is it implemented
and in which script, (ii) has it been run against current data and where
the output lives, (iii) is there a written interpretation, (iv) what's
missing. Verified directly against the codebase for this audit (grepped
for the relevant statistical machinery, read the actual scripts) rather
than assumed from memory of prior work.

**Headline correction to the prompt that requested this audit**: **H1 is
implemented, has been run, and has a written interpretation** — it was
described as unseen, but it is Comparison A under a different name. See
H1 below for the exact mapping. H3 and H4 are genuinely not implemented,
confirmed by search.

## H1 (RQ1, observational) — Paired Wilcoxon signed-rank, Dynamic vs ULT mutation score, model level

**(i) Implemented — yes.** This is **Comparison A**, not a separate
analysis: `src/Analysis/comparison.py::paired_wilcoxon` (the Wilcoxon
signed-rank + matched-pairs rank-biserial effect size + bootstrap CI),
invoked by `scripts/build_comparison_tables.py`. The pairing-unit
adaptation (model-level, not literal model-problem, since Dynamic and
ULT/PLT share no problem identity) is documented in `comparison.py`'s own
module docstring and now matches PROJECT_BRIEF.md §3.1's corrected wording
(fixed 2026-08-04, see the brief-reconciliation entry in
`analysis/OPEN_ITEMS.md`).

**(ii) Run against current data — yes.** `analysis/COMPARISON_PROVENANCE.md`
(regenerated by `scripts/build_comparison_tables.py`, re-run as part of
every close-out pass in this project). Current result: n=5 canonical
models (Qwen 32B/7B, Claude Sonnet/Haiku, Gemini Flash-Lite) with
qualifying data on both sides; raw effect_r=+0.200, p=0.8125.

**(iii) Written interpretation — yes.** `analysis/COMPARISON_A_INTERPRETATION.md`
(new 2026-08-04): the headline is a declared null — the effect's
*direction* is not stable across three independently-justified
conditionings (raw, thin-cell-filtered, definition-matched/coverage-
adjusted), so no directional claim about Dynamic-L4 vs ULT currently
survives, and the document says so explicitly rather than reporting the
single unfiltered number as if it settled the question.

**(iv) What's missing.**
- **Not corrected for multiple comparisons.** H1's p=0.8125 is reported
  raw. In practice this doesn't change anything here: RQ1's other
  hypothesis (H2, below) produces no p-value to jointly correct against,
  so RQ1 is a family of exactly one correctable p-value — Holm-Bonferroni
  on a family of one is a no-op. Still worth stating explicitly rather
  than silently relying on that being true (see the dedicated
  multiple-comparisons section below).
- **Model coverage remains incomplete** (5/9 canonical models; thin-cell
  filtering drops it further to 3/9) for reasons already fully disclosed
  (`analysis/OPEN_ITEMS.md`'s DISCLOSE-AND-PROCEED table) — not a gap in
  H1's implementation, a gap in the underlying data.

## H2 (RQ1, causal) — Difference-in-differences on the 2×3 design

**(i) Implemented — yes.** `src/Contamination/did.py::compute_did` (the
DiD estimator with bootstrap CIs), invoked by
`scripts/analyze_comparison_c.py`. This is the canonical Comparison C
(Qwen-1.5B-on-ULT LoRA, pre/post × ULT/PLT/Dynamic).

**(ii) Run — yes.** `analysis/COMPARISON_C_PROVENANCE.md` (raw tables),
generated from the completed fine-tune + eval runs (PROJECT_BRIEF.md §11:
"Comparison C — COMPLETE, both studies, 2026-07-27").

**(iii) Written interpretation — yes.** `analysis/COMPARISON_C_INTERPRETATION.md`
— the most thoroughly investigated result in the project (the monotone-
decay deviation, the Mut@K-vs-baseline-pass distinction, the selection-
effect audit, all covered).

**(iv) What's missing.** **H2 produces no formal p-value at all** —
`compute_did` reports an effect size (percentage-point DiD) with a
bootstrap CI, never a null-hypothesis-test p-value. This is consistent
with §3.1's own stated philosophy ("effect sizes with CIs are primary;
p-values support") but means there is nothing for Holm-Bonferroni to
correct for H2 specifically, and — combined with H1's point above — means
RQ1 as a whole has no live multiple-comparisons exposure under the
current reporting style, whatever the letter of §3.1's correction
requirement says.

## H3 (RQ2) — Spearman ρ between tier index and mutation score, per model and pooled

**(i) Implemented — no.** Confirmed by search: `spearmanr` /
`compute_correlations` (`src/Analysis/correlation.py`) is called only
from RQ5-family scripts (`analyze_rq5.py`, `analyze_rq5_cross_family.py`,
`analyze_rq5_diagnostics.py`, `plot_rq5_correlation.py`) — always
correlating two *benchmarks'* scores against each other (Dynamic vs ULT,
Dynamic/ULT vs BigCodeBench), never tier-index against mutation_score.
No script anywhere treats tier as an ordinal 1-4 variable and correlates
it against score.

**(ii) Run — no**, for the same reason.

**(iii) Written interpretation — no formal one**, though **substantial
descriptive groundwork already exists and would feed directly into this
test without new data collection**: the tier-discrimination gradient
(`analysis/RQ5_INTERPRETATION.md`, `analysis/METRICS_AND_FINDINGS_EXPLAINED.md`
finding #3 — L1 range 0.017, L4 range 0.366 across all 9 canonical
models) and `analysis/stability_stablemut_by_tier.csv`'s per-model,
per-tier StableMut@K means are exactly the inputs H3 needs; they have
just never been run through an actual `spearmanr(tier_index, score)` call
and reported as a correlation coefficient with a CI/p-value.

**(iv) What would need to be built.** A small new script (no new data
required — every Dynamic result row already has `tier` and
`mutation_score`): for each of the 9 canonical models, map tier to an
ordinal 1-4 and correlate against that model's per-problem
`mutation_score` (only defined rows, per this project's own conditioning
convention); separately compute a pooled version (either all models'
rows together, or a correlation of the 4 tier-means against tier index,
which is a much lower-power n=4 test per model). **Anticipated result
shape, stated as a caution, not a finding**: most canonical models sit at
or near ceiling (0.98-1.00) at L1-L2 and only differentiate at L3-L4
(`analysis/RQ5_DIAGNOSTICS.md`'s discrimination audit) — a Spearman ρ
computed naively across all 4 tiers for a near-ceiling model will be
compressed/attenuated by the ceiling effect at the easy end, similar in
spirit to the tier-pooling distortion already found and disclosed for
RQ5 (`analysis/VALIDATOR_SWEEP.md`/`MUTANT_COUNT_SPEC_AUDIT.md`'s
adjacent discussion of tier composition). This should be anticipated in
the analysis plan for H3, not discovered after the fact the way RQ5's
pooling issue was.

## H4 (RQ3) — Tier × benchmark interaction term in a mixed-effects regression, model as random effect

**UPDATE 2026-08-05: CLOSED, not built — supervisor-approved.** The
analysis below (written 2026-08-04, preserved unedited) correctly
identified the gap and its cause; the design memo it points to
(`analysis/H4_DESIGN_MEMO.md`) went on to recommend building a Dynamic-
only mixed model (option (b)). Pinzhen Chen's decision instead was option
(c) — declare H4 untestable-by-construction, build nothing. See
`PROJECT_BRIEF.md` §3.1's H4 row and `analysis/OPEN_ITEMS.md` for the
current, authoritative status; the (i)-(iv) analysis immediately below is
historical record of the investigation, not a live TODO.

**(i) Implemented — no.** Confirmed by search: no mixed-effects/
regression code exists anywhere in `scripts/` or `src/`, and
**`statsmodels` (or any other mixed-model library) is not even an
installed or declared dependency** (`pyproject.toml` has no such entry;
`import statsmodels` fails in this project's own venv). This is a bigger
gap than "the analysis wasn't run" — the infrastructure to run it doesn't
exist yet.

**(ii) Run — no.**

**(iii) Written interpretation — no.**

**(iv) What would need to be built — and a structural problem to resolve
first, not just code to write.** RQ3 asks "are static benchmarks more
prone to overestimating performance at *lower* tiers than higher ones, vs
the dynamic benchmark?" — this presupposes ULT/PLT has multiple tiers to
compare a slope across, the same way Dynamic does. **It doesn't**: ULT is
CC-filtered by its own authors to CC≥10 (this project's own independent
recomputation: CC≥8 after this project's own filter,
`analysis/ULT_DATA_QUALITY_AUDIT.md` finding 2) and every ULT/PLT record
that enters this project's comparisons is, by construction, "L4-only" —
`data/raw/ult_plt/PROVENANCE.md`: *"Comparison A/B against ULT/PLT are
therefore inherently L4-only."* A tier × benchmark interaction term
cannot be meaningfully estimated when one side of the interaction
(ULT/PLT) has zero variance in the "tier" variable — the regression would
either fail to identify the interaction term or silently estimate
something other than what RQ3 asks.

**The likely resolution, not yet decided or built**: ULT/PLT does have a
CC-quartile *band* structure already computed for Comparison B
(`data/raw/ult_plt/subsample_manifest.json`'s `band` field, consumed by
`src/Analysis/comparison.py::matched_cc_table` — CC8-9/CC10-11/CC12-15/
CC16+ bands already reported in `comparison_b_matched_cc.csv`). Using
these CC bands as ULT/PLT's tier-analog (in place of Dynamic's L1-L4,
which are also CC-based) would give the interaction term actual variance
to estimate on both sides — but this is a **design decision that hasn't
been made or agreed**, not an implementation detail, since it changes
what "benchmark" and "tier" mean well beyond a code change. Building H4
requires, in order: (1) deciding whether CC-quartile bands are an
acceptable tier-analog for ULT/PLT, (2) adding a mixed-model dependency,
(3) reshaping data into long format (one row per model×tier×benchmark
cell, mutation_score as outcome, model as a random-effect grouping
factor), (4) fitting and interpreting the interaction term. None of this
exists today.

**(i) Implemented — yes.** `src/Analysis/stability.py::pairwise_kendall_tau`
+ `stable_mut_at_k`, invoked by `scripts/analyze_stability.py`.

**(ii) Run — yes.** `analysis/STABILITY.md` (current N=4 mean pairwise
τ=0.635; all-pairs including instantiation 5: τ=0.661; full per-pair
table with each pair's own `n_models`, τ, and p-value).

**(iii) Written interpretation — yes.** `analysis/STABILITY_INTERPRETATION.md`

`analysis/METRICS_AND_FINDINGS_EXPLAINED.md`'s error ledger).

**(iv) What's missing.** **Not corrected for multiple comparisons** — the
per-pair table reports 6 (N=4 scope) or 10 (all-pairs) separate p-values,

Holm-Bonferroni or equivalent adjustment applied across them. This is a
genuine, non-trivial exposure (see the dedicated section below) — unlike
H1/H2, RQ4/H5 clearly does run multiple tests within its own family.

**Side note on RQ4.2-4.4**: PROJECT_BRIEF.md §3 lists RQ4.2 (within-family

## H6 (RQ5) — Pearson r + Spearman ρ between mutation score and proxy Pass@1

**(i) Implemented — yes.** `src/Analysis/correlation.py::compute_correlations`
(Pearson r, Spearman ρ, Kendall τ, each with bootstrap CI + permutation
p-value), invoked by `scripts/analyze_rq5.py` and
`scripts/analyze_rq5_cross_family.py`.

**(ii) Run — yes.** `analysis/RQ5_PROVENANCE.md` (canonical, n=3 vs
BigCodeBench, n=7 Dynamic↔ULT), `analysis/RQ5_CROSS_FAMILY_PROVENANCE.md`
(cross-family, n=7 vs BigCodeBench, n=11 Dynamic↔ULT) —
`analysis/rq5_correlation_PROVENANCE.md` /
`rq5_cross_family_correlation_PROVENANCE.md` for the correlation-specific
figures.

**(iii) Written interpretation — yes**, the most extensively revised
document in the project: `analysis/RQ5_INTERPRETATION.md` (diagnosis,
cross-family extension, the pre-registered validity-zone verdict, the
2026-08-04 cross-definition reconciliation).

**(iv) What's missing.** **Not corrected for multiple comparisons, and
this is the family with the most real exposure in the whole project.**
Counting the distinct correlation tests reported under the RQ5/H6 umbrella:
Dynamic↔ULT (canonical + cross-family), Dynamic↔BigCodeBench (canonical +
cross-family), ULT↔BigCodeBench (canonical + cross-family) — 6 pairs,
each reported under BOTH raw conditional Mut@K and coverage-adjusted
Mut@K = **up to 12 distinct p-values**, none adjusted for the fact they're
all being read as evidence for or against the same construct-validity
question. This doesn't necessarily change the qualitative reading (the
coverage-adjusted correlations are mostly at p<0.01, comfortably below
even a conservative correction threshold at n=12), but it has never been
checked explicitly, and the raw-metric correlations (several already at
p>0.1 uncorrected) would only get weaker, not stronger, under correction —
so the current framing is not at risk of a corrected result flipping a
"significant" finding to "not significant," only of an already-weak
finding looking marginally weaker still.

## Multiple-comparisons correction — confirmed absent everywhere, exposure varies by family

Searched the entire codebase (`analysis/`, `scripts/`, `src/`, `tests/`)
for `holm`, `bonferroni`, `multipletests`, and any other multiple-testing
adjustment mechanism: **zero hits, anywhere.** Holm-Bonferroni "within
each RQ family" (PROJECT_BRIEF.md §3.1) has never been implemented for
any RQ. Practical exposure differs sharply by family:

- **RQ1 (H1+H2): no live exposure.** H2 (DiD) reports no p-value at all;
  H1 (Wilcoxon) is the family's only p-value, and correcting a family of
  one is a no-op. The letter of the spec is unmet; the practical
  consequence is nil under this project's own CI-primary reporting style.
- **RQ2 (H3), RQ3 (H4): not yet applicable — neither hypothesis is built.**
  Flagged prospectively: if H3 is built as "per model AND pooled" (10
  correlations), it will need correction the moment it exists.
- **RQ4 (H5): real, current exposure.** 6-10 pairwise Kendall τ tests per
  snapshot, each with its own uncorrected p-value, individually described
  as "significant" or not in the current write-up.
- **RQ5 (H6): the largest real, current exposure.** Up to 12 distinct
  correlation p-values across canonical/cross-family × raw/coverage-
  adjusted × three benchmark pairs, none adjusted.

**This is added to `analysis/OPEN_ITEMS.md` as BLOCKING-FOR-SUBMISSION**
(below), scoped to RQ4 and RQ5 specifically, since those are the two
families with actual, current multiple-comparisons exposure — RQ1's gap
is real but consequence-free under the current reporting style, and
RQ2/RQ3 have nothing to correct until they're built in the first place.
