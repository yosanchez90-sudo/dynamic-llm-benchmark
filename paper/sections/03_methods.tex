\section{Benchmark Design and Experimental Setup}
\label{sec:methods}

\subsection{Template Grammar and Complexity Tiers}
\label{sec:methods-templates}
DyMuT is built from sixty hand-authored templates, each specifying a body skeleton with parameter placeholders, a parameter-domain specification, a reference oracle implementation, and a docstring template with synonym variation. A \emph{benchmark instantiation} is one full generator run: fifteen templates per tier, four tiers, five instances per template, giving 300 problems per instantiation. Templates are stratified across four cyclomatic-complexity (CC) tiers~\cite{mccabe1976complexity} -- L1 (Trivial, CC 1, single-path pure transformations), L2 (Branching, CC 2--3, disjoint conditional logic), L3 (Iterative, CC 4--7, one or two loops with boundary conditions), and L4 (Compositional, CC ${\geq}8$, nested branches and loops with multiple failure modes), with target mutant-count bands of 5--10, 10--15, 15--25, and 25--40 respectively, each centred on a per-template measured count $\pm3$ rather than a strict tier-wide cutoff, so a shared boundary value can appear in either of two adjacent tiers' bands. Cyclomatic complexity is computed statically at template-validation time and recomputed on every generated instance to confirm tier membership, since parameter sampling can shift a generated instance's control-flow shape. Prior to use, the full sixty-template corpus passed a within-tier diversity check and a tier-separation sanity check, both required by the study's corpus validation gate.

\subsection{Seeded Instantiation and Oracle-by-Construction Scoring}
\label{sec:methods-instantiation}
Each template yields fresh problem instances by sampling its parameter domain: variable names, literal values, constants, and docstring phrasing all vary across instances, under a deterministic seed, so a given (template, seed) pair reproduces identically while distinct seeds differ. This is what separates DyMuT from a static release: its problem space is the template grammar and parameter domains, not a fixed instance set, so no single generated instantiation can be memorised by a model. Correctness comes from construction: every generated instance carries a reference implementation produced alongside it from the same template, so scoring never depends on a separately curated set of expected outputs.

\subsection{Mutation Operators and Metrics}
\label{sec:methods-metrics}
Test quality is scored by mutation testing, an established proxy for a suite's fault-detection ability~\cite{jia2011mutation}, using seven semantic-altering-change (SAC) operators (Arithmetic/Relational/Logical Operator Replacement, Constant Replacement, Boundary Mutation, Statement Deletion, Return/Statement Mutation) applied as single-edit mutants. Four metrics are recorded per problem: \emph{Exec@K}, whether the suite is imported and collected without error (a gate, not a quality measure); \emph{baseline\_pass\_rate}, whether it passes against the correct implementation; \emph{Mut@K}, the fraction of mutants killed; and \emph{coverage\_adjusted}, Mut@K multiplied by baseline\_pass\_rate. Naming follows the Pass@K naming convention as used in~\cite{chen2025dycodeeval} ($K$ attempts per problem; every result here uses $K=1$); $m$ is instances per template, $N$ is benchmark instantiations. Each operator is construct-gated, not tier-gated; the supporting report gives a worked example and exact applicability condition per operator.

Mut@K is \emph{conditional}: its mean is taken only over problems whose generated suite already passes the baseline-correctness gate (\texttt{baseline\_pass}=true), excluding non-passing problems from the average entirely rather than scoring them zero. This is the pre-registered primary metric throughout this study. \texttt{coverage\_adjusted} is an unconditional reading of the same data, averaging Mut@K over every attempted problem with non-passing suites (scored zero) and is reported as a co-primary metric, not a replacement. The two readings measure different quantities and can disagree for a model with a low baseline-pass rate. ``Coverage'' in \texttt{coverage\_adjusted} is inherited ULT/PLT naming for this baseline-pass-rate adjustment, not code (statement/branch) coverage.

\subsection{Models}
\label{sec:methods-models}
Nine models from four providers were evaluated: three closed-source frontier/efficient pairs from OpenAI (\texttt{gpt-5}/\texttt{gpt-5-mini}), Anthropic (Claude Sonnet 4.6/Claude Haiku 4.5), and Google (Gemini 3.1 Pro Preview/Flash-Lite -- a forced substitution for the originally specified Gemini 2.5 Pro/Flash, which returned model-unavailable errors); and a three-point open-source scaling sweep (Qwen2.5-Coder, 32B/7B/1.5B). Every model call is logged with identifier, snapshot, decoding parameters, seed, and timestamp; a fine-tuned checkpoint is a distinct model identity from its base weights. Text generation uses temperature \DecodeTemperature{} with top-$p$ \DecodeTopP{} across all models, except the two reasoning-class OpenAI models, which reject a custom sampling temperature and run at the provider's own fixed default. $K=\DecodeK{}$ throughout; results are single-sample and the benchmark itself has no circular dependency on those results. % cite:external -- "1.5"/"3.1"/"2.5" are model name/version/parameter-count identifiers (Qwen2.5-Coder, Gemini 3.1, Gemini 2.5), not result values

All open-source models are decoder-only, instruction-tuned transformers; closed-source architectures are undisclosed. The two OpenAI models are reasoning-class, the reason they alone reject a custom sampling temperature (above). Four further open-source models (DeepSeek-Coder-6.7B, CodeLlama-13B, StarCoder2-15B, Mistral-7B) extend the H6 clause 1 check (Section~\ref{sec:results-h6clause1}) beyond the three-model Qwen family; their BigCodeBench Pass@1 scores come from the published leaderboard, not a self-run~\cite{zhuo2025bigcodebench}. % cite:external -- "6.7"/"13"/"15"/"7" are model parameter-count identifiers, not result values

Every model's ULT and PLT evaluation uses \texttt{core\_400}, a fixed 400-problem sample per benchmark (seed 42, CC-stratified) so paired per-problem comparisons (H1, RQ4) run over identical problems. A ULT pair is \emph{repair-verified} if its shipped test passes the reference implementation, unmodified or after repair, and re-verified by the harness; otherwise it is \emph{structurally unrepairable}.

\subsection{Fine-Tuning on ULT to Create Contamination}
\label{sec:methods-finetune}
To identify contamination-driven score inflation causally, the smallest open-source model (Qwen2.5-Coder-1.5B-Instruct) is fine-tuned via low-rank adaptation (LoRA)~\cite{hu2022lora} directly on ULT's ground-truth test suites, restricted to the subset with a repair-verified training pair (112 of the 400-problem subsample; the remaining 288 structurally unrepairable form a held-out unseen-ULT population). The fine-tuned checkpoint is re-evaluated on ULT, PLT, and a fresh DyMuT instantiation, using a $2{\times}3$ difference-in-differences design~\cite{angrist2009mostly} (pre/post $\times$ \{ULT, PLT, dynamic\}) with confidence intervals~\cite{efron1993bootstrap}. A DyMuT control restricted to complexity tiers L1--L3 (outside ULT/PLT's complexity floor) separates generic fine-tuning improvement from contamination-specific inflation. LoRA targets all seven attention and feed-forward projection matrices at rank \FtLoraR{}, alpha \FtLoraAlpha{}, dropout \FtLoraDropout{}; \FtEpochs{} epochs (chosen to run past the point Figure~\ref{fig:onset} shows memorisation saturating) at learning rate $\FtLearningRate{}$, cosine schedule, warmup ratio \FtWarmupRatio{}, batch size \FtPerDeviceBatch{}$\times$\FtGradAccum{}, \FtMaxLength{}-token context, \FtTrainPairs{} pairs, matching the six supplementary runs (Section~\ref{sec:results-h2supp}) exactly. These \FtTrainPairs{} pairs are drawn from ULT's broader repair-verified pool, not only \texttt{core\_400}; \HTwoSeenN{} overlap with it, defining the seen-ULT population evaluated. The design assumes parallel pre-treatment trends; Figure~\ref{fig:onset}'s shared epoch-0-to-1 jump across all three arms, before the seen-only curve diverges, is the evidence. % cite:external -- "1.5" is the model's own parameter-count identifier (Qwen2.5-Coder-1.5B-Instruct), not a result value

\subsection{Equivalent-Mutant Validation}
\label{sec:methods-equivmut}
The mutation operators applied here can generate mutants semantically equivalent to the original program and therefore unkillable by any correct test suite~\cite{jia2011mutation}, depressing the raw mutation score without reflecting a genuine test-quality gap. This is a pre-specified limitation, not an incomplete method: the correction design (120 mutants, thirty per tier) was fixed in advance, so the raw score reported throughout is a conservative \emph{lower bound}, uniformly across models, and no comparison here depends on the correction being applied. The hand-inspection converting that sample into a corrected companion score was not complete at the time of writing; this does not change any reported comparison, since the same uniform floor applies to every model alike.

\subsection{Experimental Environment}
\label{sec:methods-environment}
All compute ran on Kelvin2, QUB's HPC cluster, on a shared sliced A100, a full A100 or H100 for the two largest open-source models, and V100 nodes as a queue-depth fallback, chosen per job by model size. Software is Python \PyVersion{} with dependencies pinned by \texttt{uv}, CUDA 12.1, and the pinned library stack (\texttt{torch}, \texttt{transformers}, \texttt{peft}, \texttt{trl}, \texttt{vllm}) the supporting report's environment section lists in full. % cite:external -- PyVersion and CUDA are pinned version identifiers, not result values

The repository and every table and figure in this paper regenerate from result files on disk with a single command, \texttt{scripts/build\_thesis\_assets.py}, gated by an automated check that a hand-written document cites no number the pipeline does not currently produce.
