\section{Benchmark Design and Experimental Setup}
\label{sec:methods}

\subsection{Template Grammar and Complexity Tiers}
\label{sec:methods-templates}
DyMuT is built from sixty hand-authored templates, each specifying a body skeleton with parameter placeholders, a parameter-domain specification, a reference oracle implementation, and a docstring template with synonym variation. A \emph{benchmark instantiation} is one full generator run: fifteen templates per tier, four tiers, five instances per template, giving 300 problems per instantiation. Templates are stratified across four cyclomatic-complexity (CC) tiers~\cite{mccabe1976complexity} -- L1 (Trivial, CC 1, single-path pure transformations), L2 (Branching, CC 2--3, disjoint conditional logic), L3 (Iterative, CC 4--7, one or two loops with boundary conditions), and L4 (Compositional, CC ${\geq}8$, nested branches and loops with multiple failure modes), with target mutant-count bands of 5-10, 10-15, 15-25, and 25-40 respectively. Cyclomatic complexity is computed statically at template-validation time and recomputed on every generated instance to confirm tier membership, since parameter sampling can shift a generated instance's control-flow shape. Prior to use, the full sixty-template corpus passed a within-tier diversity check and a tier-separation sanity check, both required by the study's corpus validation gate.

\subsection{Seeded Instantiation and Oracle-by-Construction Scoring}
\label{sec:methods-instantiation}
Each template yields fresh problem instances by sampling its parameter domain: variable names, literal values, constants, and docstring phrasing all vary across instances, under a deterministic seed, so a given (template, seed) pair is reproduced identically across runs while distinct seeds produce different problem content. This is what separates DyMuT from a static release. Its problem space is defined by the template grammar and the parameter domains, not by a fixed set of instances. No single generated instantiation can be memorised by a future model. Correctness comes from construction. Every generated instance carries a reference implementation, produced alongside it from the same template, so scoring never depends on a separately curated set of expected outputs.

\subsection{Mutation Operators and Metrics}
\label{sec:methods-metrics}
Test quality is scored by mutation testing~\cite{demillo1978hints, jia2011mutation}, whose mutation score is an established proxy for a suite's fault-detection ability~\cite{andrews2005mutation}, using seven semantic-altering-change (SAC) operators: Arithmetic Operator Replacement, Relational Operator Replacement, Logical Operator Replacement, Constant Replacement, Boundary Mutation, Statement Deletion, and Return/Statement Mutation, applied as single-edit mutants. Semantic-preserving-change operators are out of scope for this study. Four metrics are recorded per problem: \emph{Exec@K}, whether the generated suite is imported and collected by the test runner without error (a gate, not a quality measure); \emph{baseline\_pass\_rate}, whether the suite passes against the original, correct implementation (the precondition for mutation scoring); \emph{Mut@K}, the fraction of mutants killed; and \emph{coverage\_adjusted}, Mut@K multiplied by baseline\_pass\_rate. Naming follows Pass@K convention, where $K$ denotes attempts per problem; every result in this study uses $K=1$. The number of sampled instances per template is denoted by $m$. $N$ denotes the number of independent benchmark instantiations (full regenerations under a fresh seed).

Mut@K is \emph{conditional}: its mean is taken only over problems whose generated suite already passes the baseline-correctness gate, excluding non-passing problems from the average entirely rather than scoring them zero. This is the pre-registered primary metric throughout this study. \texttt{coverage\_adjusted} is an unconditional reading of the same data, identical to averaging Mut@K over every attempted problem with non-passing suites (scored zero) and is reported as a labelled co-primary, not a replacement. The two readings measure different quantities and can disagree widely for a model with a low baseline-pass rate.

\subsection{Models}
\label{sec:methods-models}
Nine models spanning four providers were evaluated: three closed-source frontier/efficient pairs from OpenAI (\texttt{gpt-5}/\texttt{gpt-5-mini}), from Anthropic (Claude Sonnet 4.6/Claude Haiku 4.5), and from Google (Gemini 3.1 Pro Preview/Flash-Lite). A three-point open-source scaling sweep (Qwen2.5-Coder~\cite{hui2024qwen25coder}, 32B/7B/1.5B parameters). The Google pair is a forced substitution for the originally specified Gemini 2.5 Pro/Flash, which returned model-unavailable errors ahead of their provider's own stated retirement schedule. Every model call is logged with model identifier, snapshot or revision, decoding parameters, seed, and timestamp; fine-tuned checkpoints are treated as a distinct model identity from their base weights, since adapter identity changes what is being measured even when the base model field is unchanged. Decoding is nucleus sampling at temperature \DecodeTemperature{} and top-$p$ \DecodeTopP{}, requested identically for every model and every benchmark, with a fixed seed; the two reasoning-class OpenAI models reject a custom sampling temperature and run at the provider's own fixed default instead, a documented exception rather than an uncontrolled difference. \texttt{no\_repeat\_ngram\_size} is deliberately left unset for every model: an earlier uncommitted attempt to set it corrupted the system prompt's own required import line and produced a fabricated fine-tuning collapse, recorded in this project's error ledger. $K=\DecodeK{}$ throughout, one sampled attempt per problem; nothing in this study is tuned against the outcome metric. % cite:external -- "1.5"/"3.1"/"2.5" are model name/version/parameter-count identifiers (Qwen2.5-Coder, Gemini 3.1, Gemini 2.5), not result values

\subsection{Fine-Tuning on ULT to Create Contamination}
\label{sec:methods-finetune}
To identify contamination-driven score inflation causally, not just observationally, the smallest open-source model (Qwen2.5-Coder-1.5B-Instruct) is fine-tuned via low-rank adaptation (LoRA)~\cite{hu2022lora} directly on ULT's ground-truth test suites, restricted to the subset of ULT problems for which a repair-verified training pair could be constructed (112 of the 400-problem evaluation subsample; the remaining 288 problems, structurally unrepairable by the same verification pipeline, form a held-out unseen-ULT population). The fine-tuned checkpoint is then re-evaluated on ULT, on PLT, and on a fresh DyMuT instantiation, using a $2{\times}3$ difference-in-differences design~\cite{angrist2009mostly} (pre/post fine-tuning $\times$ \{ULT, PLT, dynamic\}) with bootstrap confidence intervals~\cite{efron1993bootstrap}, following this study's preference for effect sizes with intervals over point-estimate hypothesis tests. A DyMuT control population restricted to the two lower complexity tiers (L1--L3, outside ULT/PLT's own complexity floor) separates any generic fine-tuning improvement from contamination-specific inflation. LoRA is applied to all seven attention and feed-forward projection matrices at rank \FtLoraR{}, alpha \FtLoraAlpha{}, dropout \FtLoraDropout{}; training runs for \FtEpochs{} epochs at learning rate $\FtLearningRate{}$ on a cosine schedule with warmup ratio \FtWarmupRatio{}, batch size \FtPerDeviceBatch{} with \FtGradAccum{} gradient-accumulation steps (effective batch \FtEffectiveBatch{}), and a \FtMaxLength{}-token training context, on \FtTrainPairs{} repair-verified pairs. None of these was tuned against DyMuT or ULT score: rank, alpha, dropout, and schedule match this project's six other supplementary fine-tuning runs (Section~\ref{sec:results-h2supp}) exactly, chosen once for a LoRA configuration that fits a single shared GPU slice, not re-searched per condition. The epoch axis in Figure~\ref{fig:onset} runs to the same \FtEpochs{}-epoch endpoint reported here; a checkpoint at that epoch is the final saved adapter, not an early-stopped one. % cite:external -- "1.5" is the model's own parameter-count identifier (Qwen2.5-Coder-1.5B-Instruct), not a result value

\subsection{Equivalent-Mutant Validation}
\label{sec:methods-equivmut}
The mutation operators applied here can generate mutants that are semantically equivalent to the original program and therefore unkillable by any correct test suite~\cite{jia2011mutation}, which would depress the raw mutation score without reflecting a genuine test-quality gap. This is a pre-specified, deliberately bounded limitation, not an incomplete method: the correction design (a stratified sample of 120 mutants, thirty per complexity tier, fixed seed) was fixed in advance, and the raw, unadjusted mutation score reported throughout this study is therefore a conservative \emph{lower bound} on the true mutation score, uniformly across models, so no comparison in this paper depends on the correction being applied. The hand-inspection needed to convert that sample into an estimated equivalent-mutant rate and a corrected companion score was not complete at the time of writing; it does not change any reported comparison, since the same uniform floor applies to every model alike.

\subsection{Statistical Procedure}
\label{sec:methods-stats}
Every research-question family with more than one significance test is corrected together with the Holm-Bonferroni procedure~\cite{holm1979simple} through one shared function, applied before any result is quoted: RQ1 (H1 Test 1, H1 Test 2; $n=2$; H2's bootstrap confidence interval is not part of this family), RQ4 (pairwise cross-instantiation stability comparisons, corrected separately for the four-instantiation headline set and the all-pairs set including a partial fifth instantiation), and RQ5 (the correlation tests behind H6's two clauses, canonical and cross-family scopes, raw and coverage-adjusted metrics, three statistics). Correction changes a verdict, not only a number: H1 Test 2's primary reading (raw $p=\HOneTTwoP{}$) no longer clears \SigLevel{} once corrected ($p=\HOneTTwoRawHolmP{}$), while its coverage-adjusted co-primary does ($p=\HOneTTwoAdjP{}\rightarrow\HOneTTwoAdjHolmP{}$), which is why Section~\ref{sec:results} reports that verdict as significance-conditional rather than quoting one reading alone. A result is flagged thin, not excluded, when a model's defined-mutation-score count falls below $n_{\text{defined}}=20$; every table reporting such a cell marks it rather than silently reporting a mean over a small sample. The pre-registered validity band against which H6's correlations are judged is Kendall $\tau\in[\HSixBandLow{},\HSixBandHigh{}]$. The difference-in-differences design (Section~\ref{sec:methods-finetune}) assumes parallel pre-treatment trends between the fine-tuned model and its DyMuT control arms; Figure~\ref{fig:onset} is the evidence for this assumption, not merely an illustration of the result: all three plotted arms share the same epoch-0-to-1 jump, the signature a shared, treatment-independent trend would produce, before the seen-only curve diverges from epoch five onward.

\subsection{Experimental Environment}
\label{sec:methods-environment}
All compute ran on Kelvin2, Queen's University Belfast's SLURM-scheduled HPC cluster, on a shared sliced A100, a full A100 or H100 for the two largest open-source models, and V100 nodes as a queue-depth fallback, chosen per job by model size. Software: Python \PyVersion{}, dependencies pinned by \texttt{uv}, with \texttt{transformers} \TransformersVersion{}, \texttt{peft} \PeftVersion{}, \texttt{torch} \TorchVersion{}, \texttt{pytest} \PytestVersion{}, \texttt{coverage} \CoverageVersion{}, \texttt{pandas} \PandasVersion{}, and \texttt{scipy} \ScipyVersion{} (the Holm-Bonferroni correction itself is a hand-implemented function on top of \texttt{numpy}, not a \texttt{statsmodels} call). % cite:external -- every version macro in this sentence is a pinned third-party package version identifier, not a result value

At the 2026-08-12 experimental freeze that closed data collection for this study, 172 of 180 model-by-tier-by-instantiation cells were complete (95.6\%); the remaining gap, both Gemini models' fifth benchmark instantiation (600 problems, 8 cells), was quantified at \$9.60 to close and declined on the diagnostic grounds given in Section~\ref{sec:results-h5}. Every model call logs its identifier, snapshot, resolved decoding configuration, and seed (Section~\ref{sec:methods-models}); OpenAI's Batch API is used at half the real-time rate wherever it is supported.
